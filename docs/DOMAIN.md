# Предметная область

Это каноническое описание бизнес-терминов и правил MVP. Архитектурное состояние
и программные контракты вынесены в [ARCHITECTURE.md](ARCHITECTURE.md) и
[API.md](API.md).

## Термины и сущности

| Термин | Значение в проекте |
| --- | --- |
| Символ (`Symbol`) | Один линейный торговый инструмент; пример — `BTCUSDT` |
| Свеча (`Candle`) | OHLCV, оборот, время открытия и признак окончательного подтверждения |
| Open interest, OI | Числовой открытый интерес по символу в определённый момент |
| Ликвидация (`Liquidation`) | Сторона ликвидированной позиции, цена, количество и время; USD-значение равно `Price × Qty` |
| Снимок (`Snapshot`) | Свечи, текущее OI, накопленные ликвидации и время сбора |
| Сигнал (`Signal`) | Решение стратегии `LONG`, `SHORT` или `NONE` с причиной |
| Ордер (`Order`) | Результат запроса на открытие позиции у биржи |
| Позиция (`Position`) | Текущее направление, количество, средняя цена и время открытия |
| Сделка (`Trade`) | Сохраняемая запись от открытия до закрытия с PnL |
| Cooldown | Пауза, запрещающая новую сделку после закрытия предыдущей |
| Баланс | Внешний вход risk/execution в USD; источник в проекте ещё не определён (`TODO`) |

`SideLong`/`SideShort` используются и для направления позиции, и для стороны
ликвидированной позиции. Преобразование сторон из конкретных ответов Bybit ещё не
реализовано и должно быть подтверждено тестами адаптера (`TODO`).

Для linear-контрактов публичный адаптер получает OI и объём свечи в базовом
активе, turnover — в котируемом. Стратегия использует относительное изменение OI,
поэтому абсолютная единица не преобразуется.

## Правила формирования сигнала

Стратегия получает минимум 21 свечу. Последняя считается текущей, а предыдущие
20 используются для среднего объёма:

```text
oiGrowthPercent = (currentOI - previousOI) / previousOI × 100
volumeSMA20 = sum(volume предыдущих 20 свечей) / 20
liquidationUSD = price × qty
```

Если `previousOI <= 0`, рост OI считается равным нулю. Пороговые сравнения
строгие: значение должно быть **больше**, а не равно настройке.

### LONG

Сигнал `LONG` возникает, только когда одновременно выполнены условия:

1. рост OI больше `strategy.oi_growth_percent`;
2. объём текущей свечи больше `SMA20 × strategy.volume_multiplier`;
3. текущая свеча бычья: `Close > Open`;
4. сумма short-ликвидаций в окне последних пяти минут больше
   `strategy.liquidation_threshold` USD.

### SHORT

Сигнал `SHORT` возникает при тех же условиях OI и объёма, но текущая свеча должна
быть медвежьей (`Close < Open`), а порог применяется к long-ликвидациям.

Во всех остальных случаях возвращается `NONE` с текстовой причиной. Причина
предназначена для диагностики и хранения, а не является стабильным машинным
кодом.

### Границы временного окна

Ликвидация включается, если её время не раньше `Now - 5m`; событие ровно на
границе включается. Текущая реализация не отбрасывает события после `Now` и не
проверяет совпадение `Liquidation.Symbol` с `Input.Symbol`. Также стратегия не
требует `Candle.Confirmed == true`. Нужно решить, являются ли эти свойства
ошибками входных данных или обязанностью стратегии (`TODO`).

REST kline не возвращает отдельный признак закрытия. Адаптер вычисляет
`Confirmed` сравнением конца минутного интервала с `time` из envelope Bybit.

## Управление риском

Текущая модель фиксированного риска:

```text
riskUSD = balance × riskPerTradePercent / 100
priceRisk = entryPrice × stopLossPercent / 100
qty = riskUSD / priceRisk
```

Для `LONG` stop loss ниже цены входа, take profit выше; для `SHORT` — наоборот:

| Сторона | Stop loss | Take profit |
| --- | --- | --- |
| `LONG` | `entry × (1 - SL% / 100)` | `entry × (1 + TP% / 100)` |
| `SHORT` | `entry × (1 + SL% / 100)` | `entry × (1 - TP% / 100)` |

В примерной конфигурации риск равен 1%, SL — 0,8%, TP — 1,6%, то есть номинальное
отношение риска к прибыли 1:2. Неположительные или не конечные баланс, цена и
настройки, неизвестная сторона, а также расчёты с не конечными или
неположительными результатами отклоняются.

Расчёт пока не учитывает плечо, доступную маржу, комиссии, проскальзывание,
минимальный номинал, шаг количества и точность цены. Округление и денежный тип не
определены (`TODO`) — отправлять рассчитанный `float64` в биржу без нормализации
нельзя.

## Торговые ограничения

- MVP работает с одним настроенным символом.
- Одновременно разрешена не более чем одна открытая позиция по проверяемому
  символу.
- После закрытия действует cooldown 10 минут согласно исходной спецификации.
  `Executor` получает длительность через конструктор, поэтому composition root
  должен явно передать это значение.
- Любой сигнал сохраняется до проверки его типа и торговых ограничений, если
  `SignalStore` подключён. Ошибка сохранения останавливает исполнение.
- `NONE` не создаёт ордер.

`Executor` сериализует попытки исполнения и после успешной отправки ордера
сохраняет в памяти признак активной позиции. До вызова `MarkPositionClosed`
следующие ордера отклоняются, даже если биржа ещё не успела отразить позицию.
Метод также сохраняет время последнего закрытия для cooldown; никто в приложении
его пока не вызывает. Состояние теряется после перезапуска, а источник факта
закрытия — `TODO`.

## Хранение и статистика

Модель хранения содержит:

- `signals`: символ, тип, человекочитаемая причина и время создания;
- `trades`: символ, сторона, цены входа/выхода, количество, PnL и времена
  открытия/закрытия.

Статистика строится только по строкам с `closed_at`:

- `TotalTrades` — число закрытых сделок;
- `WinRate` — доля сделок с `pnl > 0`, в процентах;
- `ProfitFactor` — валовая прибыль / модуль валового убытка; при отсутствии
  убытков текущее значение остаётся `0`, семантика требует решения (`TODO`);
- `TotalPnL` и `AverageTrade` — сумма и среднее PnL;
- `MaxDrawdown` — максимальное падение накопленного PnL от предыдущего пика при
  обходе по `closed_at`.

Валюта PnL, правила расчёта exit price/PnL и обработка частичных исполнений не
определены (`TODO`).

## Вне границ MVP

Исходной постановкой исключены: несколько символов и стратегий, портфельное
управление, funding rate, long/short ratio, дисбаланс стакана, кластеры
ликвидности, ML, Telegram-бот, Web UI, Kafka, PostgreSQL и микросервисы.

Изменение этого списка требует явной задачи и записи в
[DECISIONS.md](DECISIONS.md), а не скрытого расширения текущей реализации.
