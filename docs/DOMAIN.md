# Предметная область

Это каноническое описание бизнес-терминов и правил MVP. Архитектурное состояние
и программные контракты вынесены в [ARCHITECTURE.md](ARCHITECTURE.md) и
[API.md](API.md).

## Термины и сущности

| Термин | Значение в проекте |
| --- | --- |
| Символ (`Symbol`) | Один линейный торговый инструмент; пример — `BTCUSDT` |
| Свеча (`Candle`) | OHLCV, оборот, время открытия и признак окончательного подтверждения |
| Open interest, OI | Числовой открытый интерес по символу в определённый момент |
| Ликвидация (`Liquidation`) | Сторона ликвидированной позиции, цена, количество и время; USD-значение равно `Price × Qty` |
| Снимок (`Snapshot`) | Свечи, текущее OI, накопленные ликвидации и время сбора |
| Сигнал (`Signal`) | Решение стратегии `LONG`, `SHORT` или `NONE` с причиной |
| Ордер (`Order`) | Результат запроса на открытие позиции у биржи |
| Позиция (`Position`) | Текущее направление, количество, средняя цена и время открытия |
| Сделка (`Trade`) | Сохраняемая запись от открытия до закрытия с PnL |
| Cooldown | Пауза, запрещающая новую сделку после закрытия предыдущей |
| Account info | Unified account status, margin mode и время обновления |
| Баланс | Account-level `totalAvailableBalance` Unified account в USD |
| Плечо (`Leverage`) | Текущая one-way настройка плеча linear-инструмента |

`SideLong`/`SideShort` используются и для направления позиции, и для стороны
ликвидированной позиции. В Bybit `allLiquidation` поле `S=Buy` означает
ликвидированную LONG-позицию, а `S=Sell` — SHORT; адаптер преобразует их
соответственно.

Для linear-контрактов публичный адаптер получает OI и объём свечи в базовом
активе, turnover — в котируемом. Стратегия использует относительное изменение OI,
поэтому абсолютная единица не преобразуется.

## Правила формирования сигнала

Стратегия использует только свечи с `Confirmed=true`. Последняя закрытая свеча
считается текущей, а предыдущие `strategy.volume_sma_period` закрытых свечей
используются для среднего объёма. Composition root запрашивает
`volume_sma_period + 2` свечи, поскольку самая новая минутная свеча обычно ещё
не закрыта:

```text
oiGrowthPercent = (currentOI - previousOI) / previousOI × 100
volumeSMA = sum(volume предыдущих volume_sma_period свечей) / volume_sma_period
liquidationUSD = price × qty
liquidationWindowStart = Now - strategy.liquidation_window_minutes × 1 minute
```

Если `previousOI <= 0`, рост OI считается равным нулю. Пороговые сравнения
строгие: значение должно быть **больше**, а не равно настройке.
`strategy.oi_window_minutes` выбирает интервал OI Bybit: `5`, `15`, `30`, `60`,
`240` или `1440` минут. Read-only runner обновляет значение внутри того же
timestamp, но рассчитывает следующий сигнал только после перехода к новому
timestamp OI; устаревший timestamp отклоняется.

### LONG

Сигнал `LONG` возникает, только когда одновременно выполнены условия:

1. рост OI больше `strategy.oi_growth_percent`;
2. объём текущей закрытой свечи больше
   `volumeSMA × strategy.volume_multiplier`;
3. текущая свеча бычья: `Close > Open`;
4. сумма short-ликвидаций в настроенном окне больше
   `strategy.liquidation_threshold_usd`.

### SHORT

Сигнал `SHORT` возникает при тех же условиях OI и объёма, но текущая свеча должна
быть медвежьей (`Close < Open`), а порог применяется к long-ликвидациям.

Во всех остальных случаях возвращается `NONE` с текстовой причиной. Причина
предназначена для диагностики и хранения, а не является стабильным машинным
кодом.

`EvaluateDetailed` рассчитывает диагностический снимок полностью до выбора
сигнала. Поэтому даже если раннее условие OI или объёма не прошло, в строке
сигнала сохраняются доступные значения всех текущих индикаторов: оба OI и их
timestamps, рост и порог OI, текущий объём, SMA/отношение/порог объёма,
open/close/направление сигнальной свечи, суммы LONG/SHORT-ликвидаций, их порог и
отдельные флаги каждого условия. При недостатке закрытых свечей
`indicators_complete=false`, а недоступные candle/volume-поля остаются `NULL`.
Приоритет текстовой причины не меняется: OI, затем volume, затем
direction/liquidations.

### Границы временного окна

`strategy.liquidation_window_minutes` задаётся положительным целым числом; пример
и дефолт — `5`. Одно значение управляет retention накопителя и cutoff стратегии.
Ликвидация включается, если её время не раньше
`Now - strategy.liquidation_window_minutes × 1 minute`; событие ровно на границе
включается.
Текущая реализация не отбрасывает события после `Now` и не проверяет совпадение
`Liquidation.Symbol` с `Input.Symbol`. Нужно решить, являются ли эти свойства
ошибками входных данных или обязанностью стратегии (`TODO`).

REST kline не возвращает отдельный признак закрытия. Адаптер вычисляет
`Confirmed` сравнением конца минутного интервала с `time` из envelope Bybit.

## Управление риском

Текущая модель фиксированного риска:

```text
riskUSD = balance × riskPerTradePercent / 100
totalLossPercent = stopLossPercent
                 + estimatedRoundTripFeePercent
                 + slippageAllowancePercent
priceRisk = entryPrice × totalLossPercent / 100
qty = riskUSD / priceRisk
```

Комиссия и проскальзывание — консервативные фиксированные резервы только для
размера позиции. Они уменьшают `qty`, но не сдвигают рассчитанные уровни SL/TP.

Для `LONG` stop loss ниже цены входа, take profit выше; для `SHORT` — наоборот:

| Сторона | Stop loss | Take profit |
| --- | --- | --- |
| `LONG` | `entry × (1 - SL% / 100)` | `entry × (1 + TP% / 100)` |
| `SHORT` | `entry × (1 + SL% / 100)` | `entry × (1 - TP% / 100)` |

В примерной конфигурации риск равен 1%, SL — 0,8%, TP — 1,6%, резерв round-trip
fee — 0,11%, резерв проскальзывания — 0,04%. Неположительные баланс, цена и
основные процентные настройки, не конечные числовые значения, отрицательные
резервы, неизвестная сторона или невалидные результаты расчёта отклоняются.

Перед будущей отправкой market-ордера executor получает актуальные правила
linear-инструмента. Количество округляется вниз до `qtyStep`, SL/TP — до
ближайшего `tickSize`. Затем проверяются `minOrderQty`, `maxMktOrderQty`,
`minNotionalValue`, диапазон цены и сохранение направления защитных уровней
относительно entry price. Нарушение границы отклоняет запрос до биржи.

Расчёт количества по-прежнему не использует плечо и доступную маржу; фактические
биржевые комиссии и проскальзывание не измеряются, используются только
настроенные оценки. Текущее плечо можно прочитать и структурно проверить, но
целевое значение и достаточность маржи не определены. В доменных структурах
используется `float64`, но квантование и проверка шага выполняются через точные
десятичные рациональные значения; wire-формат private API ещё не реализован.

Для расчёта риска предусмотрен `GetAccountBalance().AvailableUSD`. Цена входа
берётся из public linear ticker `lastPrice`. `ExecutionReadinessPreflight`
собирает эти значения вместе с account/position/leverage checks, но оркестратор
ещё не передаёт результат в executor, поэтому торговый цикл не активен.

## Виртуальная аналитика сигналов

Paper-trade использует фиксированный `trading.virtual_balance_usd` (`1000` в
примере), а не баланс Bybit. Для каждого `LONG`/`SHORT`, допущенного виртуальными
лимитами:

```text
signalPrice = Close последней подтверждённой сигнальной свечи
LONG entry  = signalPrice × (1 + slippageAllowancePercent / 100)
SHORT entry = signalPrice × (1 - slippageAllowancePercent / 100)
estimatedSlippageUSD = qty × abs(entry - signalPrice)
estimatedFeesUSD = qty × entry × estimatedRoundTripFeePercent / 100

LONG virtualPnL  = (exit - entry) × qty - estimatedFeesUSD
SHORT virtualPnL = (entry - exit) × qty - estimatedFeesUSD
```

SL/TP и `qty` рассчитываются `risk.Manager` от hypothetical entry и виртуального
баланса. Проскальзывание уже включено в entry, поэтому отдельно второй раз из
PnL не вычитается. Комиссия вычитается как round-trip оценка.

Выход проверяется на каждом market snapshot по следующим подтверждённым
минутным свечам: `Low/High` пересекают SL или TP. Сигнальная свеча не может
закрыть собственную виртуальную позицию. Если одна свеча касается обоих уровней,
выбирается консервативный `STOP_LOSS`; иначе причина — `STOP_LOSS` или
`TAKE_PROFIT`, цена выхода равна соответствующему уровню.

Paper-trade применяет одну позицию, UTC-день для `max_trades_per_day` и cooldown
в памяти процесса. После рестарта открытая виртуальная позиция, текущий дневной
счётчик и cooldown пока не восстанавливаются (`TODO`); уже записанная история
SQLite сохраняется, а незакрытая строка остаётся с пустыми outcome-полями.

## Торговые ограничения

Прямая интеграция с Telegram удалена в #177. Будущий Gateway/Hermes остаётся
планом #127 и пока не реализован.

- MVP работает с одним настроенным символом.
- Одновременно разрешена не более чем одна открытая позиция по проверяемому
  символу.
- Биржевой read model принимает только Bybit one-way mode (`positionIdx=0`).
  Пустая запись с нулевым size означает отсутствие позиции; hedge mode
  (`positionIdx=1/2`) отклоняется, а режим аккаунта автоматически не меняется.
- Account preflight допускает Unified account status `3`, `4`, `5` или `6`
  только с `REGULAR_MARGIN`. Classic/неизвестный account status, isolated и
  portfolio margin отклоняются; режимы автоматически не меняются.
- Leverage preflight принимает только положительное one-way значение с server
  time для того же символа. Инструмент должен иметь статус `Trading`, а плечо —
  находиться в `minLeverage..maxLeverage` и совпадать с `leverageStep`,
  отсчитанным от `minLeverage`. Проверка не выбирает целевое плечо и не вызывает
  set endpoint.
- Execution readiness последовательно требует совместимый account, отсутствие
  позиции, корректный balance с `AvailableUSD > 0`, положительные
  last/mark/index prices для того же символа и успешный leverage preflight.
  Нулевой available balance означает «не готов», но достаточность маржи для
  конкретного ордера не вычисляется.
- При наличии credentials readiness выполняется один раз на startup. Отказ
  означает только диагностический результат и не прерывает существующий public
  read-only loop; будущая торговля не должна использовать эту non-fatal
  семантику как разрешение на ордер.
- Конфигурация задаёт `trading.max_open_positions=1`,
  `trading.cooldown_minutes` и `trading.max_trades_per_day`. Paper-trade
  применяет эти границы к виртуальным входам. Текущий реальный `Executor`
  самостоятельно запрещает вторую позицию по единственному символу и принимает
  cooldown через конструктор, но composition root его не создаёт; дневной лимит
  и `dry_run` не реализованы как реальные execution gates.
- Любой сигнал сохраняется до проверки его типа и торговых ограничений, если
  `SignalStore` подключён. Ошибка сохранения останавливает исполнение.
- `NONE` не создаёт ордер.

`Executor` сериализует попытки исполнения и после успешной отправки ордера
сохраняет в памяти признак активной позиции. До вызова `MarkPositionClosed`
следующие ордера отклоняются, даже если биржа ещё не успела отразить позицию.
Метод также сохраняет время последнего закрытия для cooldown; никто в приложении
его пока не вызывает. Состояние теряется после перезапуска, а источник факта
закрытия, граница календарного дня для дневного лимита и поведение dry-run —
`TODO`.

## Хранение и статистика

Модель хранения содержит:

- `signals`: символ, тип, причина, время создания, полный диагностический снимок
  OI/volume/candle/liquidations с настроенными порогами и флагами условий,
  signal price, hypothetical entry, SL/TP, estimated fees/slippage, virtual Qty,
  времена сигнальной и закрывающей свечей, virtual exit price, exit reason и
  virtual PnL;
- `trades`: символ, сторона, цены входа/выхода, количество, PnL и времена
  открытия/закрытия.

Статистика строится только по строкам с `closed_at`:

- `TotalTrades` — число закрытых сделок;
- `WinRate` — доля сделок с `pnl > 0`, в процентах;
- `ProfitFactor` — валовая прибыль / модуль валового убытка; при отсутствии
  убытков текущее значение остаётся `0`, семантика требует решения (`TODO`);
- `TotalPnL` и `AverageTrade` — сумма и среднее PnL;
- `MaxDrawdown` — максимальное падение накопленного PnL от предыдущего пика при
  обходе по `closed_at`.

Virtual PnL хранится в USD по описанной выше модели. Статистика `Stats` пока
строится только по реальным/будущим строкам `trades`, а не по `signals`;
агрегация virtual PnL остаётся отдельной задачей (`TODO`).

## Вне границ MVP

Исходной постановкой исключены: несколько символов и стратегий, портфельное
управление, funding rate, long/short ratio, дисбаланс стакана, кластеры
ликвидности, ML, Telegram-бот,
Web UI, Kafka, PostgreSQL и микросервисы.

Изменение этого списка требует явной задачи и записи в
[DECISIONS.md](DECISIONS.md), а не скрытого расширения текущей реализации.
