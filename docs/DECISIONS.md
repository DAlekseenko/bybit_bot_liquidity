# Журнал архитектурных решений

Отдельных ADR в истории проекта нет. Решения ниже зафиксированы постфактум по
исходной постановке, текущему коду и конфигурации; причины не расширяются за
пределы этих свидетельств. Новые решения добавляйте отдельными записями, не
переписывая смысл старых.

## D-001: Модульный монолит на Go

- **Статус:** принято и реализовано.
- **Контекст:** репозиторий содержит один модуль и один исполняемый процесс с
  пакетами в `internal/`.
- **Решение:** сохранять один процесс и разделять ответственность пакетами, пока
  явно не появится необходимость в другой форме развёртывания.
- **Причина:** исходные приоритеты MVP — простота, минимум зависимостей и низкая
  связанность; микросервисы явно исключены.
- **Следствие:** `cmd/bot` является composition root, внутренние пакеты не служат
  внешним SDK.

  **Область:** D-001 описывает legacy Liquidity. Запланированный `cmd/momentum`
  (#59/#65/#86/#109/#112) — независимый runtime в том же модуле, не основание
  менять legacy entrypoint или неявно выбирать стратегию.

## D-002: Testnet и один символ как защитная граница MVP

- **Статус:** принято; public read-only адаптер реализован, торговая интеграция — нет.
- **Контекст:** пример конфигурации включает `testnet: true` и `BTCUSDT`, а
  исходный scope ограничивает систему одним символом.
- **Решение:** разрабатывать и проверять торговый путь только для Testnet и одного
  настроенного символа.
- **Причина:** ограничение масштаба и риска на этапе проверки гипотезы.
- **Следствие:** real-money deployment, несколько символов и портфельная
  координация не считаются поддерживаемыми.

## D-003: Стандартная библиотека по умолчанию

- **Статус:** принято и реализовано частично.
- **Контекст:** конфигурация читается через `bufio`, логирование использует
  `log/slog`, SQL — `database/sql`; внешних модулей нет.
- **Решение:** добавлять зависимости только для отсутствующей необходимой
  возможности.
- **Причина:** исходный приоритет минимального числа зависимостей.
- **Следствие:** загрузчик понимает лишь простую текущую структуру конфигурации;
  для SQLite всё равно требуется выбрать драйвер.

## D-004: Dependency injection и интерфейсы со стороны потребителя

- **Статус:** принято и реализовано в доменных компонентах.
- **Контекст:** collector и executor объявляют узкие интерфейсы, зависимости
  приходят через конструкторы, тесты используют fake-реализации.
- **Решение:** сохранять I/O за интерфейсами и не выполнять реальные API-вызовы в
  unit-тестах.
- **Причина:** изоляция торговых правил и проверяемость без биржи.
- **Следствие:** новые методы добавляются в минимальный потребительский контракт,
  а не автоматически в общий интерфейс.

## D-005: Фиксированная стратегия и риск для MVP

- **Статус:** принято и реализовано на уровне вычислений.
- **Контекст:** стратегия и risk manager кодируют единственный набор правил.
- **Решение:** использовать сигналы на OI/объёме/ликвидациях, фиксированный процент
  риска и уровни SL/TP; разрешить одну позицию и cooldown.
- **Причина:** это заданная гипотеза MVP; несколько стратегий и portfolio
  management исключены.
- **Следствие:** точные формулы поддерживаются в [DOMAIN.md](DOMAIN.md); изменения
  формул требуют тестов и новой записи решения.

  **Область:** правило относится к legacy Liquidity. Многосимвольный Crypto
  Momentum и его формулы имеют отдельный контракт; D-01 остаётся открытым.

## D-006: SQLite и встроенная начальная схема

- **Статус:** принято и реализовано для миграции и сигналов.
- **Контекст:** `Store.Migrate` содержит `CREATE TABLE IF NOT EXISTS` для сделок и
  сигналов, DSN указывает на локальный файл.
- **Решение:** использовать SQLite как локальное хранилище MVP и начать с
  идемпотентного создания схемы.
- **Причина:** SQLite указан исходным технологическим выбором, PostgreSQL исключён.
- **Следствие:** текущего DDL достаточно только как начального каркаса; стратегия
  версий остаётся открытой.

  **Область:** SQLite остаётся хранилищем legacy Liquidity. PostgreSQL Momentum
  (#65/#112) изолируется отдельной конфигурацией и данными, не переносит и не
  пересматривает legacy SQLite.

## D-007: Разделение постоянной документации и временного контекста

- **Статус:** частично заменено D-013 в части файла текущей задачи.
- **Контекст:** исходный `AGENT.md` совмещал цель, правила, архитектуру и критерии,
  из-за чего фактическая готовность была неотличима от целевого состояния.
- **Решение:** хранить назначение в `README`, домен/архитектуру/API/разработку в
  `docs`, общие инструкции в `AGENTS.md`, а текущую задачу и handoff — в `.ai`.
  `AGENT.md` остаётся только указателем.
- **Причина:** избежать дублирования и сделать материалы независимыми от
  конкретного инструмента.
- **Следствие:** каждый факт обновляется в своём каноническом документе, остальные
  места ссылаются на него.

## D-008: Фиксированный public REST-контракт для market data

- **Статус:** принято и реализовано 2026-07-22.
- **Контекст:** интерфейс `exchange.Client` не передаёт category или interval, а
  MVP задаёт один linear-символ и свечи 1m. Bybit OI требует интервал не меньше
  `5min`.
- **Решение:** `GetCandles` всегда запрашивает `category=linear`, `interval=1` и
  возвращает ответ в хронологическом порядке; `GetOpenInterest` запрашивает
  `category=linear`, `intervalTime=5min`, `limit=1`.
- **Причина:** закрепить минимальный контракт MVP без расширения публичного
  интерфейса и обеспечить ожидаемый стратегией порядок свечей.
- **Следствие:** другие категории и интервалы потребуют отдельного изменения
  контракта. Признак закрытия REST-свечи вычисляется по серверному времени Bybit.

## D-009: Read-only market loop перед торговым исполнением

- **Статус:** принято и реализовано 2026-07-22.
- **Контекст:** public REST-адаптер готов, но WebSocket, приватная торговля,
  SQLite-драйвер и восстановление состояния ещё не спроектированы.
- **Решение:** `cmd/bot` создаёт Bybit public REST client, collector и strategy,
  затем каждые 30 секунд собирает market snapshot, хранит предыдущий OI в памяти
  и логирует рассчитанный сигнал без вызова `execution.Executor`.
- **Причина:** это проверяет сборку фактического data path и стратегию на реальных
  public market data, не открывая позиции и не требуя секретов.
- **Следствие:** приложение теперь выполняет read-only сетевые запросы при запуске.
  Сигналы, зависящие от ликвидаций, останутся `NONE`, пока WebSocket-события не
  подключены.

## D-010: CGo-free SQLite и startup-миграция

- **Статус:** принято и реализовано 2026-07-22.
- **Контекст:** конфигурация и SQL-код уже используют SQLite, а Docker runtime
  основан на Alpine. CGo-драйвер усложнил бы сборку и потребовал C toolchain.
- **Решение:** зарегистрировать `modernc.org/sqlite` v1.39.1 под именем `sqlite`,
  проверять соединение через `Ping`, применять идемпотентный DDL при старте и
  сохранять каждый рассчитанный сигнал из read-only loop.
- **Причина:** драйвер реализует `database/sql` без CGo, поддерживает Go 1.24 и
  не меняет защитную границу Testnet/read-only относительно биржи.
- **Альтернативы:** `mattn/go-sqlite3` отклонён из-за CGo; откладывание wiring
  оставило бы уже существующий storage-контракт непроверенным в приложении.
- **Следствие:** startup теперь зависит от доступности DSN; отдельные версии и
  rollback миграций, PRAGMA/пул соединений и хранение сделок остаются TODO.

## D-011: Public all-liquidation stream и ограниченное окно

- **Статус:** принято и реализовано 2026-07-23.
- **Контекст:** стратегия требует суммы LONG/SHORT-ликвидаций за пять минут, а
  устаревший Bybit topic `liquidation` передаёт неполные данные.
- **Решение:** использовать public linear topic `allLiquidation.{symbol}`,
  преобразовывать `Buy` в ликвидированную LONG-позицию, `Sell` — SHORT, отправлять
  JSON heartbeat каждые 20 секунд и переподключаться через фиксированные 5 секунд.
  События хранятся в потокобезопасном окне пяти минут только в памяти.
- **Причина:** актуальный topic передаёт все ликвидации с частотой до 500 мс и не
  требует API credentials; ограниченное окно совпадает с контрактом стратегии.
- **Альтернативы:** deprecated topic отклонён как неполный; хранение raw events в
  SQLite отложено, поскольку восстановление пропусков самим Bybit не предоставлено.
- **Следствие:** после разрыва события за время disconnect не восстанавливаются;
  экспоненциальный backoff, jitter и observability остаются TODO.

## D-012: Env-only credentials и жёсткая граница Testnet

- **Статус:** принято и реализовано 2026-07-23.
- **Контекст:** перед private API нужно исключить случайный commit секретов и
  запуск против mainnet, сохранив возможность read-only запуска без ключей.
- **Решение:** читать опциональную полную пару `BYBIT_API_KEY` и
  `BYBIT_API_SECRET` только из process environment; секреты в YAML отклонять.
  `testnet=true` и точные официальные HTTPS/WSS Testnet endpoints обязательны.
- **Причина:** fail-fast проверка предотвращает опасную конфигурацию до создания
  сетевых клиентов, а отсутствие ключей не ломает публичный data path.
- **Альтернативы:** `.env` loader и секреты в YAML отклонены из-за риска
  случайного commit; поддержка mainnet feature flag отложена за пределы MVP.
- **Следствие:** private transport сможет получить credentials через явные
  accessor-методы; ротация, secret manager и permission policy ключа остаются
  операционными TODO.

## D-013: Текущая задача не дублируется в репозитории

- **Статус:** принято и реализовано 2026-07-23.
- **Контекст:** `.ai/CURRENT_TASK.md` переписывался после каждой итерации и
  дублировал пользовательский запрос, Git history и `.ai/HANDOFF.md`.
- **Решение:** удалить файл; scope брать из запроса пользователя или внешнего
  issue, а фактическое состояние, проверки и следующие шаги хранить в handoff.
- **Причина:** уменьшить число временных источников, которые требуется синхронно
  обновлять.
- **Следствие:** автономный участник должен получить конкретную задачу извне;
  `.ai/HANDOFF.md` не заменяет task tracker.

## D-014: Биржевые instrument rules перед PlaceOrder

- **Статус:** принято и реализовано 2026-07-23.
- **Контекст:** risk manager возвращает непрерывные `float64`, а Bybit принимает
  только значения по `qtyStep`/`tickSize` и проверяет quantity, price и notional.
- **Решение:** получать `/v5/market/instruments-info` для одного linear symbol
  непосредственно перед будущим исполнением; Qty округлять вниз, SL/TP — до
  ближайшего tick с точной десятичной рациональной арифметикой. После округления
  повторно проверять статус, границы и направление защитных уровней.
- **Причина:** исключить отклоняемые или превышающие риск заявки до private API и
  не фиксировать изменяемые биржевые лимиты в конфигурации.
- **Альтернативы:** обычная арифметика `math.Floor(value/step)` отклонена из-за
  двоичных погрешностей; внешняя decimal-зависимость не нужна для текущего scope.
- **Следствие:** каждый торговый сигнал добавляет public REST-запрос; cache/TTL,
  комиссии, проскальзывание и строковый wire-format остаются TODO.

## D-015: Execution inputs из ticker и Unified available balance

- **Статус:** принято и реализовано 2026-07-23; startup-вызов добавлен в D-020.
- **Контекст:** executor требует USD balance и entry price, а свечной close и
  wallet balance отдельной монеты не отражают актуальную цену/доступную маржу.
- **Решение:** entry price получать из public linear ticker `lastPrice`; balance —
  из account-level `totalAvailableBalance` signed endpoint для `UNIFIED`. Для GET
  реализовать HMAC-SHA256 V5 headers с receive window 5000 мс.
- **Причина:** поля напрямую соответствуют существующим входам risk manager и не
  требуют конвертации coin balance.
- **Альтернативы:** candle close отклонён как потенциально устаревший;
  `walletBalance` USDT не учитывает account-wide margin state.
- **Следствие:** требуется NTP-синхронизация часов; isolated margin не
  поддерживается. Источники ещё не подключены к торговому orchestrator.

## D-016: Read-only позиция только в one-way mode

- **Статус:** принято и реализовано на уровне адаптера 2026-07-23.
- **Контекст:** executor должен отличать отсутствие позиции от уже открытой. Bybit
  возвращает `positionIdx=0` для one-way mode и `1/2` для двух сторон hedge mode,
  тогда как доменная модель MVP допускает только одну позицию.
- **Решение:** signed `GetPosition` читает linear `/v5/position/list` по symbol.
  Нулевая one-way запись возвращает `nil`; активная преобразует side, size,
  avgPrice и createdTime. Любой hedge-mode ответ возвращает
  `ErrUnsupportedPositionMode`. Адаптер не вызывает switch-mode.
- **Причина:** fail-closed поведение сохраняет ограничение одной позиции и не
  меняет внешнее состояние аккаунта неявно.
- **Альтернативы:** поддержка двух hedge legs отклонена как выход за модель MVP;
  автоматический switch-mode отклонён как небезопасная мутация конфигурации.
- **Следствие:** Testnet account должен быть заранее настроен в one-way mode.
  При наличии credentials position read model вызывается startup readiness;
  безопасная интеграционная проверка с реальным Testnet остаётся отдельной
  задачей.

## D-017: Unified REGULAR_MARGIN account preflight

- **Статус:** принято и реализовано 2026-07-23; startup-вызов добавлен в D-020.
- **Контекст:** balance и position reads недостаточно, чтобы отличить classic
  account или неподдерживаемую модель маржи перед будущим ордером.
- **Решение:** signed `GetAccountInfo` читает `/v5/account/info`.
  `execution.AccountPreflight` допускает `unifiedMarginStatus` `3/4/5/6` только с
  `marginMode=REGULAR_MARGIN`. Остальные status/margin mode отклоняются
  sentinel-ошибками. Никакие switch/set endpoints не вызываются.
- **Причина:** текущая fixed-risk модель опирается на account-level available
  balance и не моделирует isolated или portfolio margin. Read-only preflight
  закрывает эту границу без скрытых мутаций аккаунта.
- **Альтернативы:** разрешить все Unified margin modes отклонено из-за разной
  семантики доступной маржи; автоматически переключать margin mode отклонено как
  небезопасное внешнее изменение.
- **Следствие:** Testnet account должен быть Unified и заранее настроен в
  `REGULAR_MARGIN`. Целевое leverage и runtime wiring остаются открытыми;
  account preflight покрыт fake-тестами и вызывается startup readiness только
  при наличии credentials.

## D-018: Read-only leverage preflight по instrument limits

- **Статус:** принято и реализовано 2026-07-27; startup-вызов добавлен в D-020.
- **Контекст:** Bybit предоставляет текущую настройку futures leverage даже без
  открытой позиции, а instrument info задаёт допустимые `minLeverage`,
  `maxLeverage` и `leverageStep`. Целевое плечо стратегии пока не подтверждено.
- **Решение:** signed `GetLeverage` читает linear
  `/v5/position/list` по symbol и принимает только one-way
  `positionIdx=0`. `execution.LeveragePreflight` сверяет фактическое значение с
  актуальным leverage filter через точную десятичную арифметику. Никакие
  set/switch endpoints не вызываются.
- **Причина:** fail-closed проверка обнаруживает неподдерживаемую или
  противоречивую конфигурацию до будущего ордера, не угадывая целевое плечо и не
  изменяя состояние Testnet account.
- **Альтернативы:** автоматически вызвать `set-leverage` отклонено как внешняя
  мутация без согласованной политики; фиксированное значение в коде отклонено
  как неподтверждённое бизнес-правило.
- **Следствие:** целевое leverage, достаточность доступной маржи и trading wiring
  остаются TODO. Read-only source и preflight покрыты fake transport/source
  тестами; startup reporting подключён позднее в D-020.

## D-019: Агрегированный read-only execution readiness

- **Статус:** принято и реализовано 2026-07-27; startup reporting см. D-020.
- **Контекст:** будущему executor одновременно нужны совместимый account,
  отсутствие позиции, available balance, market price и допустимое leverage.
  Отдельные sources и preflight уже реализованы, но общей fail-closed границы
  перед торговым orchestration не было.
- **Решение:** `ExecutionReadinessPreflight` через consumer-side
  `ExecutionReadinessSource` последовательно выполняет account preflight,
  проверку отсутствия позиции, валидацию balance/price и leverage preflight.
  Успех возвращает единый value snapshot. Никакие order/set endpoints не
  вызываются.
- **Причина:** одна тестируемая граница не позволяет оркестратору случайно
  пропустить обязательную read-only проверку и не связывает `execution` с
  конкретным Bybit-адаптером.
- **Альтернативы:** сразу подключить `Executor` к `cmd/bot` отклонено до появления
  private order transport и политики ошибок; вычислять required margin как
  `notional/leverage` отклонено как неподтверждённое упрощение Unified margin.
- **Следствие:** один readiness check выполняет несколько REST-запросов.
  Freshness window, target leverage, достаточность маржи для конкретного order
  plan и trading orchestration остаются TODO.

## D-020: Non-fatal startup reporting execution readiness

- **Статус:** принято и реализовано 2026-07-27.
- **Контекст:** env credentials являются явным opt-in к signed reads, но текущий
  процесс исполняет только public market-data loop и не может отправить ордер.
  Нужна диагностическая проверка интеграции без превращения временной private API
  ошибки в остановку сбора рынка.
- **Решение:** после создания authenticated client и до запуска фоновых горутин
  `cmd/bot` один раз вызывает `ExecutionReadinessPreflight`. Без credentials
  вызов пропускается. Успех логируется с symbol, ошибка — с безопасным стабильным
  `reason`; snapshot и исходный error не логируются. Ошибка non-fatal для
  существующего read-only loop.
- **Причина:** startup report проверяет весь signed путь на Testnet, не раскрывая
  account values и не снижая доступность независимого public data path.
- **Альтернативы:** startup-fatal ошибка отклонена, пока торговли нет; periodic
  polling отклонён до определения rate-limit/retry/freshness policy.
- **Следствие:** запуск с credentials выполняет несколько дополнительных REST
  запросов и может ждать их transport timeout. Перед подключением executor
  readiness должен стать обязательным gate, а non-fatal политика — пересмотрена.

## D-021: Настраиваемые параметры стратегии и risk sizing

- **Статус:** принято и реализовано 2026-07-28; заменяет фиксированный OI-интервал
  из D-008 и фиксированное liquidation-окно из D-011.
- **Контекст:** OI-окно, SMA20 и пятиминутное окно ликвидаций были зашиты в код,
  а risk sizing учитывал только расстояние до SL. Это мешало настраивать
  гипотезу из одного канонического YAML и не резервировало оценочные издержки.
- **Решение:** добавить точные поля `strategy.oi_window_minutes`,
  `oi_growth_percent`, `volume_sma_period`, `volume_multiplier`,
  `liquidation_window_minutes`, `liquidation_threshold_usd` и risk-поля
  `risk_per_trade_percent`, `stop_loss_percent`, `take_profit_percent`,
  `estimated_round_trip_fee_percent`, `slippage_allowance_percent`.
  OI-окно ограничено интервалами Bybit; сигнал считается только при новом
  timestamp OI. SMA использует только подтверждённые свечи. Одно liquidation-
  окно передаётся в accumulator и strategy. Fee/slippage входят в оценочный
  процент потерь для `qty`, но не меняют SL/TP.
- **Причина:** явные единицы в именах YAML и единый источник параметров устраняют
  расхождения между сбором данных, сигналом и расчётом позиции.
- **Альтернативы:** произвольный duration для OI отклонён как несовместимый с
  ограниченным набором Bybit; отдельные retention/signal window отклонены как
  лишняя вариативность MVP; фактические fee/slippage недоступны до реализации
  жизненного цикла исполнения.
- **Следствие:** `volume_sma_period` ограничен 998 из-за лимита kline 1000 и
  возможной незакрытой свечи; большое liquidation-окно может увеличить память.
  Fee/slippage пока являются статическими оценками, а после рестарта OI требует
  нового предыдущего timestamp.

## D-022: Trading-параметры как неактивный конфигурационный контракт

- **Статус:** конфигурация реализована 2026-07-28; execution enforcement
  отложен до подключения торгового runtime.
- **Контекст:** будущему executor нужны явные dry-run, лимит позиций, cooldown и
  дневной лимит, но `cmd/bot` пока read-only, а private order/close transport
  отсутствует.
- **Решение:** добавить `trading.dry_run`, `max_open_positions`,
  `cooldown_minutes` и `max_trades_per_day`. При отсутствии YAML `dry_run`
  по умолчанию равен `true`; канонический пример явно задаёт запрошенное
  `false`. Односимвольный MVP принимает только `max_open_positions=1`;
  временной и дневной лимиты должны быть положительными.
- **Причина:** зафиксировать единицы и настройки сейчас, не создавая ложную
  частичную торговую интеграцию.
- **Альтернативы:** подключить только cooldown к существующему `Executor`
  отклонено: это оставило бы `dry_run` и дневной лимит декларативными, но могло
  бы выглядеть как завершённая система защит.
- **Следствие:** все четыре execution-control поля загружаются и валидируются,
  однако пока не разрешают и не блокируют заявки. Перед первым вызовом
  `PlaceOrder` торговый orchestrator обязан применить dry-run, дневной лимит,
  позиционный лимит и восстановленный cooldown как единый fail-closed gate.

## D-023: Paper-trade история в signals

- **Статус:** принято и реализовано 2026-07-28.
- **Контекст:** для анализа недостаточно типа/причины сигнала: нужны цена
  сигнала, виртуальный вход, SL/TP, оценочные издержки, причина выхода и net PnL.
  Владелец выбрал виртуальный баланс `$1,000`.
- **Решение:** добавить `trading.virtual_balance_usd=1000` и pure
  `internal/papertrade`. Signal price равен Close подтверждённой сигнальной
  свечи; hypothetical entry ухудшается на настроенное slippage. Qty/SL/TP
  рассчитывает существующий risk manager, fee хранится как round-trip оценка.
  Последующие подтверждённые свечи закрывают позицию по SL/TP; одновременное
  касание обоих уровней считается `STOP_LOSS`. Net virtual PnL включает
  ухудшенный entry и вычитает estimated fee.
- **Причина:** воспроизводимая аналитика работает в read-only runtime и не
  требует private order transport или account balance.
- **Альтернативы:** actual Testnet balance отклонён как нестабильный источник;
  только новые nullable-колонки без расчёта outcome отклонены как недостаточные
  для анализа; оптимистичное разрешение неоднозначной свечи через TP отклонено.
- **Следствие:** `signals` расширена plan/outcome-полями; существующая таблица
  обновляется nullable `ALTER TABLE` без удаления истории. Активная paper-позиция,
  cooldown и дневной счётчик пока живут только в памяти, поэтому после рестарта
  незакрытая строка не восстанавливается автоматически. Virtual PnL ещё не входит
  в `storage.Stats`.

## D-024: Docker Compose с локально доступным SQLite-файлом

- **Статус:** принято и реализовано 2026-07-28.
- **Контекст:** для длительного Testnet/paper-trade прогона нужен
  воспроизводимый контейнерный запуск и сохранение SQLite между перезапусками.
  Приложение использует embedded SQLite и не имеет PostgreSQL-драйвера.
- **Решение:** `docker-compose.yml` запускает основной сервис `bot`, монтирует
  конфигурацию read-only и локальный `./data` в `/app/data`. UID/GID процесса
  задаются через `.env`, чтобы сохранить непривилегированный запуск и права
  владельца bind mount.
  Контейнер работает без root, с read-only root filesystem,
  `no-new-privileges`, ограниченной ротацией логов и SQLite healthcheck.
  Runtime-образ содержит CA-сертификаты, а тот же бинарник предоставляет
  `-check-storage` для read-only `PRAGMA quick_check`. Дополнительный
  корпоративный CA передаётся в build как BuildKit secret и монтируется на
  runtime read-only без отключения TLS verification. Опциональный профиль
  `tools` предоставляет запускаемый по требованию SQLite CLI, который подключает
  тот же каталог только для чтения и не изображает отдельный сервер БД.
- **Причина:** Compose воспроизводит фактическую архитектуру без фиктивной
  внешней СУБД, не теряет историю при обычном `docker compose down` и оставляет
  SQLite-файл непосредственно доступным владельцу проекта для анализа.
- **Альтернативы:** PostgreSQL-сервис отклонён как несовместимый с текущим
  storage-кодом и границами MVP; именованный volume использовался первоначально,
  но заменён bind mount по требованию локального доступа к файлу. Различия
  UID/permissions между платформами компенсируются явными `BOT_UID`/`BOT_GID`.
- **Следствие:** `docker compose run --rm sqlite` позволяет выполнять ручные
  read-only запросы без установки CLI на host; локальные программы могут открыть
  `./data/trades.db` напрямую. `docker compose down -v` не удаляет bind-mounted
  историю; backup, freshness healthcheck для Bybit и production monitoring
  остаются TODO.

## D-025: Полный indicator snapshot для каждого сигнала

- **Статус:** принято и реализовано 2026-07-29.
- **Контекст:** текстовая `reason` показывает только первое проваленное условие и
  не позволяет понять состояние остальных индикаторов в момент `NONE`.
- **Решение:** сохранить совместимый `Evaluate(Input) Signal` и добавить
  `EvaluateDetailed(Input) Evaluation`. Detailed path до выбора сигнала
  рассчитывает оба OI и рост, volume/SMA/ratio/threshold, open/close/направление
  свечи, обе суммы ликвидаций, timestamps, configured thresholds и отдельные
  condition/setup flags. Read-only runner сохраняет этот snapshot в typed
  nullable-колонки каждой строки `signals`. При недостатке свечей
  `indicators_complete=false`, недоступные candle/volume-поля остаются `NULL`.
- **Причина:** значения можно прямо фильтровать и сравнивать SQL-запросами, не
  парся нестабильный текст `reason`; вычисление всех индикаторов не меняет
  приоритет принятия решения.
- **Альтернативы:** хранить только первую причину отклонено как недостаточное для
  анализа; один JSON blob отклонён в пользу типизированных SQL-колонок; менять
  `Signal` и все execution-контракты отклонено ради обратной совместимости.
- **Следствие:** startup migration добавляет новые nullable-колонки без изменения
  старых строк. Таблица `signals` становится шире; при добавлении новых
  индикаторов схему и `Indicators` нужно расширять согласованно.

## D-026: Базовый CI в GitHub Actions

- **Статус:** принято и реализовано 2026-08-26.
- **Контекст:** локальные команды проверки были определены, но автоматически не
  выполнялись; потребовалось подтверждать успешность GitHub Actions после
  изменений.
- **Решение:** запускать форматирование, unit-тесты, race detector, `go vet` и
  сборку на каждом push и pull request с версией Go из `go.mod`.
- **Причина:** обеспечить одинаковый минимальный quality gate локально и в
  репозитории.
- **Следствие:** расширенный линтер, порог покрытия и интеграционные Testnet-тесты
  остаются открытыми частями CI.

## D-027: Поддерживаемый toolchain при совместимости исходников с Go 1.24

- **Статус:** обновлено 2026-10-11; совместимость исходников с Go 1.24 сохранена.
- **Контекст:** последняя версия линии Go 1.24 (`1.24.13`) снята с поддержки и
  содержит достижимые уязвимости стандартной библиотеки в TLS, HTTP, X.509 и
  URL, исправления для которых выпускаются только в поддерживаемых линиях Go.
- **Решение:** сохранить директиву `go 1.24.13` как уровень языка и совместимости
  исходников, но зафиксировать `toolchain go1.26.9`. Docker использует
  `golang:1.26.9-alpine`, а GitHub Actions читает toolchain из `go.mod`.
- **Причина:** сетевой бот не должен собираться с известными достижимыми
  уязвимостями TLS/HTTP, при этом для кода не требуются возможности языка новее
  Go 1.24.
- **Альтернативы:** остаться на Go 1.24.13 отклонено из-за результатов
  `govulncheck`; повысить директиву языка до Go 1.26 отклонено как ненужное
  изменение совместимости исходников.
- **Следствие:** стандартный `GOTOOLCHAIN=auto` при необходимости скачает Go
  1.26.9. Принудительный `GOTOOLCHAIN=local` с Go 1.24.13 компилирует код, но не
  является поддерживаемым безопасным runtime проекта.

## D-028: Личный Telegram интерфейс только для чтения

- **Статус интеграции:** withdrawn по Issue #177; исходное решение ниже сохранено как запись о прежней реализации.
- **Статус:** принято и реализовано 2026-10-03.
- **Контекст:** оператору нужен удалённый просмотр статуса процесса, публичных
  настроек и сохранённого сигнала без входа на сервер.
- **Решение:** optional long polling включается полной env-парой токена и
  положительного owner ID; принимаются только личные сообщения от этого ID в
  чате с тем же ID. Доступны `/start`, `/help`, `/status`, `/settings`, `/signal`.
  Последняя команда читает историческую SQLite-строку заданного символа.
- **Причина:** Telegram не получает полномочий менять настройки, risk или
  биржевое состояние; ошибки API не содержат токен, URL или тело ответа.
- **Альтернативы:** группы, callbacks и команды изменения состояния отложены.
- **Следствие:** owner создаёт и хранит Telegram token отдельно; подтверждение
  пользователя, подписки, уведомления и торговые операции не входят в этот интерфейс.

## D-029: Удалить прямую Telegram-интеграцию

- **Статус:** принято и реализовано по Issue #177.
- **Контекст:** прямой Telegram long polling был необязательным legacy-интерфейсом и требовал собственных credentials и сопровождения.
- **Решение:** удалить клиент, команды и передачу Telegram credentials в процесс; Gateway/Hermes остаётся отдельным планом #127.
- **Причина:** будущая Telegram-интеграция должна иметь отдельный контракт; план #127 ещё не реализован.
- **Альтернативы:** параллельный прямой интерфейс отклонён как лишний путь; считать Gateway/Hermes готовой заменой нельзя, поскольку он пока не запускается.
- **Следствие:** legacy runtime не предоставляет Telegram-команд; удалённые файлы восстанавливаются из Git.

## D-030: Patch-обновление Go toolchain для GO-2026-6809

- **Статус:** принято 2026-10-22; Go 1.26.10 включает исправление `crypto/x509`.
- **Контекст:** `govulncheck` выявил достижимую GO-2026-6809 в `Certificate.Verify`
  при Go 1.26.9. [Уязвимость](https://pkg.go.dev/vuln/GO-2026-6809) и [история
  релизов Go](https://go.dev/doc/devel/release) подтверждают исправление в 1.26.10.
- **Решение:** заменить pin Go 1.26.9 из D-027 на toolchain и Docker build image
  1.26.10, сохранив `go 1.24.13`, зависимости и действующие CI gates.
- **Следствие:** версия patch фиксирует указанную уязвимость; Testnet/read-only
  режим и runtime-поведение не меняются.
