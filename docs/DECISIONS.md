# Журнал архитектурных решений

Отдельных ADR в истории проекта нет. Решения ниже зафиксированы постфактум по
исходной постановке, текущему коду и конфигурации; причины не расширяются за
пределы этих свидетельств. Новые решения добавляйте отдельными записями, не
переписывая смысл старых.

## D-001: Модульный монолит на Go

- **Статус:** принято и реализовано.
- **Контекст:** репозиторий содержит один модуль и один исполняемый процесс с
  пакетами в `internal/`.
- **Решение:** сохранять один процесс и разделять ответственность пакетами, пока
  явно не появится необходимость в другой форме развёртывания.
- **Причина:** исходные приоритеты MVP — простота, минимум зависимостей и низкая
  связанность; микросервисы явно исключены.
- **Следствие:** `cmd/bot` является composition root, внутренние пакеты не служат
  внешним SDK.

## D-002: Testnet и один символ как защитная граница MVP

- **Статус:** принято; public read-only адаптер реализован, торговая интеграция — нет.
- **Контекст:** пример конфигурации включает `testnet: true` и `BTCUSDT`, а
  исходный scope ограничивает систему одним символом.
- **Решение:** разрабатывать и проверять торговый путь только для Testnet и одного
  настроенного символа.
- **Причина:** ограничение масштаба и риска на этапе проверки гипотезы.
- **Следствие:** real-money deployment, несколько символов и портфельная
  координация не считаются поддерживаемыми.

## D-003: Стандартная библиотека по умолчанию

- **Статус:** принято и реализовано частично.
- **Контекст:** конфигурация читается через `bufio`, логирование использует
  `log/slog`, SQL — `database/sql`; внешних модулей нет.
- **Решение:** добавлять зависимости только для отсутствующей необходимой
  возможности.
- **Причина:** исходный приоритет минимального числа зависимостей.
- **Следствие:** загрузчик понимает лишь простую текущую структуру конфигурации;
  для SQLite всё равно требуется выбрать драйвер.

## D-004: Dependency injection и интерфейсы со стороны потребителя

- **Статус:** принято и реализовано в доменных компонентах.
- **Контекст:** collector и executor объявляют узкие интерфейсы, зависимости
  приходят через конструкторы, тесты используют fake-реализации.
- **Решение:** сохранять I/O за интерфейсами и не выполнять реальные API-вызовы в
  unit-тестах.
- **Причина:** изоляция торговых правил и проверяемость без биржи.
- **Следствие:** новые методы добавляются в минимальный потребительский контракт,
  а не автоматически в общий интерфейс.

## D-005: Фиксированная стратегия и риск для MVP

- **Статус:** принято и реализовано на уровне вычислений.
- **Контекст:** стратегия и risk manager кодируют единственный набор правил.
- **Решение:** использовать сигналы на OI/объёме/ликвидациях, фиксированный процент
  риска и уровни SL/TP; разрешить одну позицию и cooldown.
- **Причина:** это заданная гипотеза MVP; несколько стратегий и portfolio
  management исключены.
- **Следствие:** точные формулы поддерживаются в [DOMAIN.md](DOMAIN.md); изменения
  формул требуют тестов и новой записи решения.

## D-006: SQLite и встроенная начальная схема

- **Статус:** принято в спецификации, частично реализовано.
- **Контекст:** `Store.Migrate` содержит `CREATE TABLE IF NOT EXISTS` для сделок и
  сигналов, DSN указывает на локальный файл.
- **Решение:** использовать SQLite как локальное хранилище MVP и начать с
  идемпотентного создания схемы.
- **Причина:** SQLite указан исходным технологическим выбором, PostgreSQL исключён.
- **Следствие:** текущего DDL достаточно только как начального каркаса; выбор
  драйвера и стратегия версий остаются открытыми.

## D-007: Разделение постоянной документации и временного контекста

- **Статус:** принято 2026-07-22.
- **Контекст:** исходный `AGENT.md` совмещал цель, правила, архитектуру и критерии,
  из-за чего фактическая готовность была неотличима от целевого состояния.
- **Решение:** хранить назначение в `README`, домен/архитектуру/API/разработку в
  `docs`, общие инструкции в `AGENTS.md`, а текущую задачу и handoff — в `.ai`.
  `AGENT.md` остаётся только указателем.
- **Причина:** избежать дублирования и сделать материалы независимыми от
  конкретного инструмента.
- **Следствие:** каждый факт обновляется в своём каноническом документе, остальные
  места ссылаются на него.

## D-008: Фиксированный public REST-контракт для market data

- **Статус:** принято и реализовано 2026-07-22.
- **Контекст:** интерфейс `exchange.Client` не передаёт category или interval, а
  MVP задаёт один linear-символ и свечи 1m. Bybit OI требует интервал не меньше
  `5min`.
- **Решение:** `GetCandles` всегда запрашивает `category=linear`, `interval=1` и
  возвращает ответ в хронологическом порядке; `GetOpenInterest` запрашивает
  `category=linear`, `intervalTime=5min`, `limit=1`.
- **Причина:** закрепить минимальный контракт MVP без расширения публичного
  интерфейса и обеспечить ожидаемый стратегией порядок свечей.
- **Следствие:** другие категории и интервалы потребуют отдельного изменения
  контракта. Признак закрытия REST-свечи вычисляется по серверному времени Bybit.
