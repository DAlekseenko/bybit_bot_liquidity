# План развития функционала (Roadmap)

Этот документ описывает поэтапный план развития и улучшения Bybit Liquidity Bot, начиная с устранения текущих архитектурных разрывов (перехода от MVP-каркаса к работающему боту) и заканчивая расширением торговых возможностей.

## Этап 1: Стабилизация MVP и базовая инфраструктура (Закрытие разрывов)

На этом этапе необходимо превратить текущий "каркас" в запускаемое приложение, способное выполнять реальные торговые операции на Testnet.

### 1.1. База данных и миграции (O-001)
- **Проблема:** Сейчас не подключен драйвер SQLite (нет импорта `github.com/mattn/go-sqlite3` или аналога на чистом Go, например `modernc.org/sqlite`), метод `Migrate` вызывается не из `main`.
- **Решение:**
  - Добавить зависимость SQLite драйвера.
  - В `cmd/bot/main.go` проинициализировать `storage.Open`, вызвать миграции и обеспечить корректное закрытие БД (`defer db.Close()`).
  - Определить политику миграций (на текущем этапе оставить `CREATE TABLE IF NOT EXISTS`, в будущем внедрить `golang-migrate/migrate`).

### 1.2. Конфигурация и секреты (O-002, O-010)
- **Проблема:** Нет механизма работы с API Key/Secret, парсер конфига примитивный, нет валидации.
- **Решение:**
  - Заменить самописный парсер на `gopkg.in/yaml.v3` для надежности (решает O-010).
  - Добавить поля `ApiKey` и `ApiSecret` в структуру конфигурации.
  - Поддержать чтение секретов из переменных окружения (например, через `godotenv` или стандартный `os.Getenv`), чтобы не светить ключи в `config.yaml`.
  - Жестко зашить защиту от Mainnet (проверка `Testnet == true` при инициализации Bybit клиента).

### 1.3. Приватный клиент Bybit (O-005, O-006)
- **Проблема:** Методы `PlaceOrder`, `GetPosition`, `ClosePosition` возвращают `ErrNotImplemented`.
- **Решение:**
  - Реализовать генерацию подписи (HMAC-SHA256) для приватных эндпоинтов Bybit V5.
  - Реализовать метод получения баланса счета (Account Info), чтобы передавать его в `risk.Manager` (решает O-006).
  - Запросить правила инструмента (Instrument Info) для получения шага цены (tick size) и шага лота (lot size). Внедрить округление количества ордера (`Qty`) и цены (`Price`, `StopLoss`, `TakeProfit`) до требуемой точности перед отправкой на биржу (решает O-005).

### 1.4. Оркестратор и Торговый цикл (O-003, O-004)
- **Проблема:** Разрозненные пакеты (`marketdata`, `strategy`, `execution`) не связаны в единый цикл, нет WebSocket-клиента.
- **Решение:**
  - Создать пакет `internal/orchestrator` (или `engine`), который:
    - По таймеру (например, раз в минуту) опрашивает `marketdata.Collector`.
    - Хранит значение предыдущего Open Interest в памяти (или БД) для расчета дельты.
    - Вызывает `strategy.Evaluate()`.
    - При наличии сигнала вызывает `execution.Execute()`.
  - Реализовать WebSocket-клиент Bybit для стриминга ликвидаций в реальном времени. Накопленные ликвидации за последние 5 минут передавать в `Collector`. Реализовать логику переподключения (reconnect) и backoff.

## Этап 2: Отказоустойчивость и безопасность торгового процесса

Этот этап посвящен повышению надежности бота при перезапусках, потере сети или частичном исполнении.

### 2.1. Жизненный цикл сделки (O-007, O-008)
- **Проблема:** Состояние `positionOpen` и `cooldown` в `executor.go` теряется при перезапуске приложения.
- **Решение:**
  - При запуске `main` выполнять синхронизацию с Bybit: проверять наличие открытой позиции и незавершенных ордеров по символу.
  - Синхронизировать локальную БД с биржей (проставлять `closed_at`, если позиция была закрыта по стопу на бирже, пока бот был оффлайн).
  - Восстанавливать состояние `cooldown`, читая время закрытия последней сделки из БД.

### 2.2. Защита от перегрузок и ошибок сети
- **Развитие:**
  - Добавить Rate Limiter для REST-запросов (соблюдение лимитов Bybit API).
  - Внедрить паттерн Retry для сетевых ошибок (таймауты, 5xx ошибки) при отправке ордеров.
  - Внедрить механизм "Аварийного выключения" (Kill Switch), который закрывает все позиции и отменяет ордера при критической ошибке (например, многократные ошибки API).

## Этап 3: Аналитика и тестирование (O-011)

### 3.1. Интеграционное тестирование
- Поднять тестовую среду (Testnet-тесты), которые реально отправляют заявки на Bybit Testnet с фейковым API-ключом, чтобы проверить корректность подписей и контрактов.

### 3.2. Расширенный мониторинг
- Вывод метрик (`stats`) в отдельный эндпоинт (HTTP server) в формате Prometheus.
- Внедрить линтер `golangci-lint` в CI/CD пайплайн.

## Этап 4: Расширение функционала (За пределами MVP)

Когда MVP работает стабильно, можно переходить к функционалу, изначально выведенному за рамки MVP.

### 4.1. Мультиинструментальность
- Перевести бота с работы над одним символом (BTCUSDT) на одновременную работу с пулом символов (ETHUSDT, SOLUSDT и др.).
- Адаптировать `storage` и `orchestrator` для параллельной обработки. Контроль позиции и cooldown должен быть на уровне отдельного символа.

### 4.2. Новые стратегии и факторы
- Добавить поддержку дополнительных стратегий. Например: Funding Rate арбитраж, анализ кластеров ликвидности (Orderbook imbalance).
- Сделать фабрику стратегий, чтобы можно было конфигурировать активные стратегии в `yaml` файле.

### 4.3. Оповещения
- Интеграция с Telegram API: отправка уведомлений в канал при открытии/закрытии позиции, достижении таргетов или ошибках.

### 4.4. Переход на PostgreSQL (Опционально)
- При увеличении объемов данных о свечах и тиках заменить SQLite на PostgreSQL для более быстрых аналитических запросов и возможности подключения BI-инструментов (Grafana, Metabase).
